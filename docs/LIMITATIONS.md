# Limits on interpretation

This is a mechanism replication of published pseudocode and a sensitivity study of its boundaries. It is not a replication of LLM task success, a production integration, or a financial system.

The original bounded search found no usable paper implementation; the [2 October review](READINESS.md#originality-and-attribution) subsequently identified related community implementations. No official author implementation was identified. The paper leaves environment semantics underdetermined. Our single compound action models the task's three stages; the original agent chose tools in a ReAct loop. Fault precedence, read delays, backoff, effect scheduling and server idempotency contracts were chosen here, locally predeclared before the implementation commit and retained in tapes. Main results estimate only these seeded fixtures. Pairing uses attempt-indexed latent faults rather than wall-clock fault exposure; methods that issue fewer calls do not consume unused attempts. Each 150-row aggregate reuses 25 seed streams across two tasks and three fault levels. Wilson bounds are descriptive and do not assert independent 95% population coverage. This is not externally timestamped/public preregistration.

The supported server is intentionally strong: durable per-stage dedupe and pending reservations. State is an in-memory Python object. This does not demonstrate SQLite, external API durability, transaction atomicity, process restart recovery or machine failure. All failures and delays are logical; there are no OS crash or concurrency experiments. The timestamp-drift test simulates recreation of the caller action with a changed bucket, not a process restart. The operation-ID alternative assumes the caller already durably preserves that ID; this repo does not supply persistent caller state.

A verifier gets only a copied visible view. Python capability objects are an interface discipline, not an adversarial security boundary. The final evaluator can read hidden state; the wrapper cannot through its public API. Read-only verification does not resolve stale false negatives, delayed future effects, incorrect domain identity, partial-stage caching, refund semantics, key expiry or key reuse. The test with two explicit identical-payload operations concerns our caller-operation identity model; real invoice APIs may correctly define the invoice ID itself as the business identity.

An incomplete invoice predicate can hide missing status. Invoice truth success permits a correct recorded record among duplicates; safe success rejects every duplicate. Activation truth already requires exactly one welcome. False success here means a reported success that fails safe completion, at return or at tick 8, as labeled. An operation that commits after the fixed tick-8 horizon is outside this model. Definite failures are not retried by literal/engineering modes. No policy is promised to win.

The stress set deliberately includes failures at equal weights. Its success rates are coverage summaries, not forecasts. Five seeds vary payloads for identical prescribed schedules; they do not create independent random fault trajectories. No p-values, throughput benchmark, deployed SLA, exactly-once delivery guarantee, real payments, customer data, network, external action or paid model call is claimed.
